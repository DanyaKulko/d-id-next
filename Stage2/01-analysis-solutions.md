# Stage 2 — Анализ путей решения

## Как сейчас работает система (для контекста)

Пользователь говорит → Azure распознаёт речь → текст уходит на наш сервер → сервер пересылает в D-ID → D-ID обрабатывает через свой RAG (векторный поиск по знаниям) + LLM → генерирует ответ → аватар произносит ответ через WebRTC стрим.

**Ключевой момент:** Мы контролируем текст, который уходит в D-ID. Это наша главная точка влияния — мы можем модифицировать запрос пользователя перед отправкой.

# Задача 1: Внешние источники (новости, погода, актуальные данные)

## Суть проблемы
D-ID использует только свою базу знаний (статьи блога, тренировочные данные). Он не знает, что происходит в мире прямо сейчас. Нужно, чтобы аватар мог отвечать на вопросы про актуальные события.

## Варианты реализации

### Вариант А: Обогащение запроса на нашей стороне (рекомендую)

**Как работает:** Перед отправкой в D-ID мы перехватываем вопрос, определяем что нужен внешний поиск, делаем поиск, и вставляем результат прямо в текст сообщения как подсказку для D-ID.

Пользователь спросил: "Что говорит Трамп?"
В D-ID уходит: "Что говорит Трамп? <ext_source>За последние дни Трамп заявлял о... [данные из поиска]</ext_source>"

D-ID видит подсказку и использует её при генерации ответа.

**Плюсы:**
- Не трогаем D-ID вообще — он просто получает более богатый контекст
- Полный контроль — мы решаем когда искать, что подставлять
- Можно менять поисковый движок в любой момент
- D-ID нативно умеет работать с контекстом в сообщении

**Минусы:**
- Добавляет задержку (2-5 секунд на поиск) — пользователь ждёт дольше
- Если поиск вернул мусор — аватар может дать некачественный ответ
- Ограничение по длине сообщения в D-ID API (нужно следить за размером подсказки)

**Риски и сложности:**
- Главная сложность — **задержка**. Поиск занимает 2-5 секунд + D-ID генерация 3-5 секунд = 5-10 секунд ожидания. Решение: пока идёт поиск, показать pre-rendered видео типа "Хороший вопрос, дайте подумать..."
- Качество поиска зависит от формулировки запроса. Иногда пользователь говорит невнятно, и поиск вернёт не то.

### Вариант Б: Отдельный LLM-слой перед D-ID

**Как работает:** Вместо простого поиска мы сначала отправляем вопрос в свой LLM (GPT-4o) с web search, получаем полноценный ответ, и этот ответ подставляем как контекст для D-ID.

**Плюсы:**
- Более качественная обработка — LLM может отфильтровать нерелевантное
- Можно комбинировать данные из нескольких источников

**Минусы:**
- Двойная задержка: наш LLM (2-4 сек) + D-ID LLM (3-5 сек) = 5-9 секунд минимум
- Двойная стоимость (платим и за свой LLM, и за D-ID)
- Избыточность — D-ID и так использует LLM для генерации ответа

### Вариант В: Параллельный ответ (наш LLM отвечает вместо D-ID)

**Как работает:** Для "актуальных" вопросов мы полностью обходим D-ID RAG и генерируем ответ своим LLM с web search, а D-ID используем только для озвучки (Text-to-Speech).

**Плюсы:**
- Максимальный контроль над качеством ответа
- Не зависим от ограничений D-ID RAG

**Минусы:**
- Ломает D-ID контекст разговора (D-ID не будет знать что "он сказал")
- Сложная реализация — нужно посылать готовый текст в D-ID как script, а не как chat
- Теряем D-ID "личность" (persona, стиль ответа) для этих вопросов
- Сложнее поддерживать

**Рекомендация: Вариант А.** Он самый простой, надёжный и не ломает существующий flow. Задержку решаем через pre-rendered "thinking" видео.

## Подзадача: Как определять, что нужен внешний поиск?

### Подход 1: Только ключевые слова (рекомендую для старта)

Список слов-триггеров: "новости", "погода", "последние", "актуальные", "сегодня", "вчера", "news", "weather", "latest", "current", "today" и т.д.

**Плюсы:** Мгновенно (0ms), бесплатно, предсказуемо, легко отлаживать
**Минусы:** Пропустит неочевидные запросы ("Что сейчас в мире происходит?" — нет ключевого слова)

### Подход 2: LLM-классификатор (gpt-4o-mini)

Каждое сообщение сначала отправляется в мини-LLM который решает: это про актуальное или нет?

**Плюсы:** Понимает контекст, не пропустит неочевидные запросы
**Минусы:** +300-500ms к каждому сообщению (даже обычному), стоимость за каждый запрос

### Подход 3: Ключевые слова + LLM fallback (оптимальный баланс)

Сначала проверяем ключевые слова (0ms). Если есть совпадение — сразу решение. Если нет — вызываем LLM-классификатор.

**Плюсы:** Быстрый для очевидных случаев, умный для неочевидных
**Минусы:** Для неочевидных запросов всё равно +300-500ms задержка

**Рекомендация: Подход 3.** Для 70-80% запросов сработают ключевые слова мгновенно. Для остальных LLM добавит небольшую задержку, но не пропустит важное. При этом LLM-классификацию можно включить/выключить в настройках агента.

## Подзадача: Какой API для поиска?

### OpenAI Responses API + web_search (рекомендую)

**Плюсы:** API ключ уже есть в проекте, одна экосистема, хорошее качество, поддержка multiлингвальных запросов
**Минусы:** Стоимость ~$0.02-0.05 за запрос

### Perplexity API

**Плюсы:** Специализирован на поиске, может быть точнее для новостных запросов
**Минусы:** Нужен отдельный API ключ, отдельный аккаунт, ещё одна зависимость

**Рекомендация: OpenAI.** Уже интегрирован, меньше зависимостей. Если качество не устроит — легко переключить на Perplexity позже.

# Задача 2: Медиа-роутинг (показ фото)

## Суть проблемы
Когда пользователь просит "покажи фото из Турции", нужно найти подходящие фото и показать их рядом с аватаром.

## Источники фото

### Внутренний (блог) — основной

**Как работает:** У нас уже есть cron worker, который парсит статьи из блога. Расширяем его: при парсинге статей извлекаем также картинки (URL + описание/alt text). Сохраняем в новую таблицу `media_assets` с описанием.

**Плюсы:** Контролируемый контент, релевантный аватару, быстрый доступ (из своей БД)
**Минусы:** Ограниченный набор (только то, что есть в блоге)

**Главная сложность:** Качество описаний. Если у картинки в блоге нет alt text (часто бывает), нужно как-то сгенерировать описание. Варианты:
- **GPT-4o vision** — отправить картинку, получить описание. Качественно, но дорого и медленно при массовом парсинге
- **Контекст из статьи** — взять заголовок + окружающий текст. Бесплатно, но менее точно
- **Рекомендация:** Использовать контекст из статьи (заголовок + ближайший параграф) как описание. Дёшево и достаточно для поиска.

### Внешний (поиск картинок) — fallback

**Как работает:** Если в своей базе нет подходящих фото, делаем поиск через OpenAI / Google Images API.

**Плюсы:** Неограниченный контент
**Минусы:** Непредсказуемое качество, задержка на поиск, возможные проблемы с авторскими правами

**Рекомендация:** Начать с внутренней базы. Внешний поиск картинок добавить как Phase 2 — он не критичен для MVP.

## Как искать подходящие фото в базе?

### Подход 1: Полнотекстовый поиск PostgreSQL (рекомендую)

Используем встроенный `tsvector/tsquery` PostgreSQL для поиска по описаниям.

**Плюсы:** Уже есть (PostgreSQL — наша БД), быстро (~5-20ms), бесплатно
**Минусы:** Не понимает семантику ("Стамбул" не найдёт "Турция"), работает хуже для коротких запросов

### Подход 2: Embeddings (векторный поиск)

Генерируем векторные embeddings для каждого описания, ищем по семантической близости.

**Плюсы:** Понимает семантику, лучше для неточных запросов
**Минусы:** Нужно pgvector расширение, генерация embeddings при загрузке, дороже и сложнее

### Подход 3: LLM-ранкинг

Достаём кандидатов простым поиском, потом LLM выбирает самые подходящие.

**Плюсы:** Самое высокое качество отбора
**Минусы:** +500-1000ms задержка, стоимость за каждый запрос

**Рекомендация: Подход 1 для старта.** PostgreSQL full-text search покрывает 80% случаев. Если качество не устроит — добавить embeddings позже. Учитывая что фото из блога конкретного человека, точных совпадений по словам будет достаточно.

## Показ фото на фронтенде

CSS для медиа-панели (`.na-media-panels`, `.na-photo-grid`) **уже написан** в проекте, но не используется. Нужно только:
1. Создать React-компонент, который рендерит фото в этой сетке
2. Добавить его в layout страницы аватара
3. Показывать/скрывать при получении медиа из сервера

**Сложностей минимум** — это чистый фронтенд без внешних зависимостей.

# Задача 4: Pre-rendered видео (заготовленные клипы)

## Суть проблемы
Нужно воспроизводить заготовленные видео-клипы при определённых событиях: молчание пользователя, долгое "думание" аватара, прерывание, ошибка. Это создаёт эффект живого общения.

## Ключевой архитектурный вопрос: Как показать pre-rendered видео?

### Вариант А: Overlay поверх D-ID стрима (рекомендую)

**Как работает:** Pre-rendered видео — отдельный `<video>` элемент, который накладывается поверх D-ID стрима через CSS (z-index). Когда нужно показать клип — меняем opacity с 0 на 1. Когда клип закончился — обратно.

**Плюсы:**
- Простая реализация
- D-ID стрим остаётся подключённым (не нужно переподключаться)
- Плавные переходы через CSS transition
- Нет зависимости от D-ID API

**Минусы:**
- Два видео-элемента одновременно (может быть проблема на слабых устройствах)
- На iOS есть ограничения на одновременное воспроизведение нескольких видео

**Риск iOS:** Safari ограничивает количество одновременных медиа-элементов. Решение: при показе pre-rendered видео ставить D-ID стрим на mute (не удаляем, просто приглушаем). Нужно тестировать.

### Вариант Б: Отправка pre-rendered видео через D-ID API (stream script)

**Как работает:** Используем D-ID API `sendStreamScript()` чтобы D-ID сам проиграл заготовленный текст/аудио.

**Плюсы:** Нативная интеграция, нет проблем с двумя видео

**Минусы:**
- D-ID генерирует видео в реальном времени (задержка 2-3 секунды) — теряется мгновенность реакции
- Не можем использовать заранее записанные видео с высоким качеством lip-sync
- Зависим от D-ID API

### Вариант В: Подмена src у video-элемента

**Как работает:** Останавливаем D-ID стрим, меняем source видео-элемента на pre-rendered файл, после окончания переподключаем D-ID.

**Плюсы:** Один видео-элемент
**Минусы:** Нужно переподключать WebRTC стрим (1-3 секунды задержка, возможные сбои)

**Рекомендация: Вариант А.** Самый быстрый и надёжный. Проблема iOS решаема. Переподключение стрима (Вариант В) слишком рискованно.

## Триггеры и таймеры

Вся логика на клиенте (в браузере):

| Событие | Условие | Вероятность | Сложность |
|---------|---------|-------------|-----------|
| Молчание пользователя | Статус "listening" > 10 сек | 100% | Низкая — простой setTimeout |
| Аватар думает | Статус "thinking" > 10 сек | 100% | Низкая — простой setTimeout |
| Прерывание | Нажатие кнопки "Interrupt" | 33% | Низкая — Math.random() |
| Ошибка | Статус "error" | 100% | Низкая |

**Порядок видео:** Round-robin (0 → 1 → 2 → ... → N → 0). Для каждого типа события свой счётчик.

**Потенциальная проблема:** Если pre-rendered видео играет, а пользователь заговорил — нужно прервать клип и вернуться к стриму. Решается через обработку события `onSpeechDetected` → `setIsPlaying(false)`.

## Хранение и загрузка видео

Видео хранятся локально на сервере в `public/uploads/prerendered/`. Загружаются через админку.

**Потенциальная проблема:** Размер видео. 10-секундный клип в хорошем качестве — 5-15 МБ. Если 20 клипов на агента = 100-300 МБ. При загрузке страницы НЕ загружаем все видео — подгружаем по мере необходимости (lazy loading). Первый клип каждого типа можно preload.

# Общая картина задержек (latency budget)

| Сценарий | Без Stage 2 | С Stage 2 |
|----------|-------------|-----------|
| Обычный вопрос | 3-5 сек | 3-5 сек (без изменений) |
| Вопрос с ключевым словом → internal search | — | 3-5 сек (keyword: 0ms + D-ID) |
| Вопрос → external search | — | 5-10 сек (поиск 2-5 сек + D-ID) |
| Вопрос → неочевидный + LLM classifier | — | 5.5-10.5 сек (LLM 0.5 сек + поиск + D-ID) |
| Показ фото из БД | — | 3-5 сек (поиск в БД: 20ms) |

**Вывод:** Заметная задержка только для external search (5-10 сек). Решается pre-rendered "thinking" видео — пользователь видит реакцию аватара через 0.5 сек, а полный ответ приходит через 5-10 сек.

# Порядок реализации (что делать первым)

1. **Pre-rendered видео** — даёт максимальный UX-эффект при минимальной сложности. Чистый фронтенд + простая таблица в БД + админка для загрузки.

2. **External search (обогащение запросов)** — ядро Stage 2. Зависит от pre-rendered видео (нужен "thinking" клип для задержки).

3. **Медиа-панель (фото)** — фронтенд + парсинг из блога. CSS уже написан.

4. **Медиа-панель (видео)** — аналогично фото, добавляем после.
