# Stage 2 — Улучшения и дополнения к ТЗ

Этот документ содержит выявленные проблемы, пробелы и конкретные улучшения к текущему ТЗ Stage 2. Структура повторяет ТЗ — для каждого раздела указаны проблемы и предлагаемые доработки.

---

## 1. Роутинг интента через ключи и LLM классификатор

### 1.1 Проблема: Двухшаговая классификация избыточна при текущей схеме

**Текущее ТЗ:** Сначала проверяем ключевые слова. Если есть хоть 1 совпадение — подтверждаем через LLM.

**Проблема:** Если ключевое слово сработало на "покажи фото из Турции" — это уже очевидный intent `photo_from_blog`. Отправлять его в LLM для подтверждения = +300-500ms задержки без пользы. LLM-классификатор нужен только когда ключевые слова **НЕ** сработали.

**Улучшение:** Инвертировать схему:
- Ключевые слова сработали → **сразу** используем результат без LLM
- Ключевые слова **не** сработали → отправляем в LLM для классификации
- Исключение: если ключевые слова дают **неоднозначный** результат (совпали слова из 2+ категорий одновременно, например "покажи последние фото новости") — тогда LLM разрешает конфликт

### 1.2 Проблема: Ключевые слова на 7 языках — ложные срабатывания

**Текущее ТЗ:** Проверяем на наличие слов на всех 7 языках.

**Проблемы:**
- Слово "сегодня" в контексте "Сегодня я хочу узнать о детстве Нейла" — не требует external search, но ключевое слово сработает
- Некоторые слова на разных языках могут быть омонимами
- Короткие слова на Hindi/Marathi могут входить как подстрока в другие слова

**Улучшения:**
- Использовать **word boundary matching** (регулярные выражения `\b`), а не простой `includes()`
- Учитывать **контекст слова**: "покажи фото" = intent, но "ты делал фото?" = вопрос о факте, не запрос медиа. Решение: привязывать ключевые слова к **паттернам фраз**, а не отдельным словам. Например: `покажи + фото`, `есть + видео`, `найди + новости`
- Для Hindi/Marathi/Indonesian — предварительно нормализовать текст (убрать diacritics для Hindi Devanagari не нужно, но убрать лишние пробелы, знаки). Протестировать каждый язык отдельно — word boundary `\b` не работает корректно для Devanagari и других нелатинских скриптов. Для этих языков использовать пробел/начало/конец строки как границу слова

### 1.3 Проблема: Отсутствует учёт истории диалога в классификаторе

**Текущее ТЗ:** Промпт LLM упоминает "историю беседы", но ТЗ не описывает как именно она передаётся.

**Улучшение:** Описать конкретно:
- В LLM-классификатор передавать последние **3-5 сообщений** из `ChatMessage` для данной сессии
- Это критично для follow-up вопросов: "А покажи ещё" (без контекста непонятно что показать — фото или видео)
- Текущий код в `chatAction()` уже загружает историю чата — переиспользовать
- **Лимит контекста:** Суммарно не более 1000 токенов истории для классификатора (gpt-4o-mini). Обрезать старые сообщения

### 1.4 Проблема: LLM-классификатор — формат промпта недостаточно строгий

**Текущее ТЗ:** Промпт описывает 5 интентов + none, но не задаёт чёткие правила разрешения неоднозначностей.

**Улучшения к промпту:**
- Добавить **приоритет**: если запрос содержит и "покажи фото" и "актуальные новости" — что выбрать? Предлагаемый приоритет: `search_information` > `photo/video_from_blog` > `photo/video_from_external` > `none`
- Добавить правило: **если запрос упоминает Нейла/его блог/его путешествия** → `_from_blog`. Если **нет явного контекста Нейла** → `_from_external`
- Добавить `language` в JSON ответ — LLM определяет язык запроса, это нужно для формирования ключевых слов на английском
- Добавить **примеры** (few-shot) в промпт — минимум 2-3 примера на каждый intent. Без примеров gpt-4o-mini часто ошибается на edge cases

**Дополнение к JSON ответу:**
```json
{ "intent": "photo_from_blog", "keywords": "Turkey, Grand Canyon", "language": "en" }
```

### 1.5 Проблема: Не описан таймаут LLM-классификатора

**Улучшение:** Добавить в ТЗ:
- Таймаут LLM-классификатора: **2 секунды**
- Если таймаут сработал → считать intent = `none`, отправлять в D-ID как обычно
- Мониторинг: логировать в `ExternalServiceLog` все таймауты классификатора

### 1.6 Дополнение: Стоимость и rate limits

**Проблема не упомянута в ТЗ:** Каждое сообщение пользователя потенциально вызывает LLM-классификатор.

**Нужно добавить:**
- Оценка стоимости: gpt-4o-mini ~$0.15/1M input tokens. При промпте ~500 токенов + 200 токенов история = ~700 tokens/запрос. При 1000 запросов/день = $0.10/день. Допустимо.
- Rate limit: OpenAI имеет лимиты на RPM (Requests Per Minute). Для gpt-4o-mini лимит обычно 500 RPM. При 10 одновременных пользователях — не проблема. Но заложить обработку 429 ошибки (retry с backoff или fallback на `none`)

## 2. Поиск по ключевым словам (PostgreSQL tsvector)

### 2.1 Проблема: Режим `simple` теряет важные возможности поиска

**Текущее ТЗ:** Используем `simple` конфигуратор.

**Проблема:** `simple` не делает стемминг — поиск "travel" не найдёт "travels", "traveling", "travelled". Для английских описаний это потеря 20-30% релевантных результатов.

**Улучшение:** Использовать `english` конфигуратор для `tsvector`, так как:
- Подписи генерируются на английском (по ТЗ LLM keywords тоже на английском)
- `english` поддерживает стемминг: "travel" → найдёт "travels", "traveling"
- `english` убирает стоп-слова: "the", "a", "in" не засоряют индекс
- Для поискового запроса использовать `plainto_tsquery('english', $keywords)` — это безопаснее чем `to_tsquery` (не требует специального синтаксиса)

### 2.2 Проблема: Нет fallback при нулевом результате FTS

**Текущее ТЗ:** Ищем по tsvector. Если 0 результатов для блога → идём в Google/YouTube.

**Проблема:** Между "точное совпадение FTS" и "внешний поиск" нет промежуточного шага. Если пользователь написал "Grand Canyon sunset", а описание содержит "beautiful evening at Grand Canyon" — FTS может не найти (нет слова "sunset").

**Улучшение:** Добавить промежуточный шаг — `ILIKE` поиск по отдельным словам:
1. `tsvector @@ tsquery` — точный FTS
2. Если 0 результатов → `description ILIKE '%grand%' AND description ILIKE '%canyon%'` — грубый поиск по подстрокам
3. Если всё ещё 0 → внешний поиск

### 2.3 Проблема: Не описано обновление searchVector при изменении описания

**Улучшение:** Добавить в ТЗ:
- При вставке/обновлении записи `MediaAsset` — автоматически пересчитывать `search_vector`
- Реализовать через PostgreSQL триггер (в миграции), а не в коде приложения — так надёжнее:
```sql
CREATE OR REPLACE FUNCTION update_media_search_vector()
RETURNS trigger AS $$
BEGIN
  NEW.search_vector := to_tsvector('english', COALESCE(NEW.title, '') || ' ' || COALESCE(NEW.description, ''));
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER media_search_vector_update
  BEFORE INSERT OR UPDATE ON media_assets
  FOR EACH ROW EXECUTE FUNCTION update_media_search_vector();
```

## 3. Подготовка контента из блога

### 3.1 Проблема: GPT-4o Vision для анализа фото — стоимость и скорость

**Текущее ТЗ:** Используем GPT-4o для анализа фото (URL + контекст статьи → подпись).

**Проблемы:**
- GPT-4o vision: ~$0.01-0.03 за изображение. Если в блоге 500 постов по 5 фото = 2500 фото = $25-75 за первичный парсинг
- Скорость: ~2-3 секунды на фото = 2500 * 2.5сек = ~1.7 часа на полный парсинг
- Rate limits OpenAI: при большом количестве фото можно упереться в лимит

**Улучшения:**
- **Первичный парсинг**: Для первой загрузки использовать **контекст статьи** (заголовок + ближайший параграф + alt text) как описание. Это бесплатно и мгновенно. Покрывает 70-80% случаев
- **Vision как опция**: GPT-4o Vision использовать только для фото **без alt text и без контекста** (когда описание получилось пустое или слишком короткое < 20 символов)
- **Батчинг**: Обрабатывать фото пачками по 5-10, не по одному. Один запрос GPT-4o может содержать несколько изображений
- **Инкрементальность**: CRON обрабатывает только **новые** посты (как уже делает текущий worker). Не пересчитывать фото для уже обработанных постов
- Добавить флаг `captionSource: "context" | "vision" | "manual"` в модель — чтобы потом можно было пересчитать только "context" записи через vision если качество поиска окажется недостаточным

### 3.2 Проблема: Не описана структура данных от Blog API для фото

**Текущее ТЗ:** "API блога возвращает фото вместе с данными поста."

**Улучшение:** Конкретизировать. Текущий API (`malinicms.com/api/v2/posts`) возвращает поля:
- `description` — HTML тело статьи, содержит `<img>` теги
- `introduction` — краткое описание

Нужно документировать:
- Какой формат `<img>` тегов? (src, data-src, srcset?)
- Есть ли отдельное поле с массивом фото (gallery)?
- Есть ли thumbnails/featured image?
- Какие домены у фото? (нужно для CSP на фронтенде)

**Рекомендация:** Сделать пробный запрос к API и задокументировать реальную структуру ответа перед началом разработки.

### 3.3 Проблема: Не описана обработка "битых" фото-ссылок

**Улучшение:** Добавить:
- При парсинге проверять доступность URL фото (HEAD запрос, статус 200)
- Пометить `isEnabled = false` для недоступных
- CRON периодически (раз в неделю?) проверяет доступность существующих фото

### 3.4 Проблема: Видео из блога — формат транскрипции

**Текущее ТЗ:** "Транскрибация видео уже готово в блоге и отдается по API."

**Уточнение:** В текущей модели `ApiPost` есть поле `video_transcript`. Это и есть транскрипция. Но:
- Не описан формат: plain text? SRT? VTT? С таймкодами?
- Текущий worker (`knowledge-cron-worker.ts`) уже обрабатывает `video_transcript` для Knowledge Base (строка 264: `buildRawSourceText` включает `video_transcript`)
- **Нужно:** Использовать тот же cleaned text как описание для поиска, НО сократить его (max 500 символов) для `searchVector`. Полная транскрипция может быть очень длинной — tsvector не предназначен для документов 10k+ символов

### 3.5 Проблема: URL видео — откуда берётся?

**Текущее ТЗ:** "URL оригинального видео (api) на сайте блога."

**Проблема:** Текущая `ApiPost` модель не содержит отдельного поля `video_url`. Видео может быть:
- YouTube iframe внутри `description` HTML
- Прямая ссылка на mp4
- Vimeo embed
- Нужно парсить HTML `description` и извлекать видео-ссылки

**Улучшение:** Добавить в ТЗ конкретную логику парсинга:
1. Ищем `<iframe src="youtube.com/embed/...">` → извлекаем YouTube ID → формируем embed URL
2. Ищем `<video src="...">` → прямая ссылка
3. Ищем `<iframe src="vimeo.com/...">` → Vimeo embed
4. Приоритет: YouTube > прямая ссылка > Vimeo

## 4. Внешние источники знаний (search_information)

### 4.1 Проблема: "Параллельный запрос" — непрактично для текущей архитектуры

**Текущее ТЗ:** "Параллельно, независимо от триггера, мы всегда запрашиваем данные из ext_source."

**Проблема:** Это значит что **каждое** сообщение пользователя (включая "привет", "спасибо", "как тебя зовут") вызывает web search. При OpenAI web_search ~$0.02-0.05/запрос и 100-500 сообщений в день = $2-25/день на бесполезные запросы.

**Улучшение:** Параллельный запрос делать **только** когда keyword matcher нашёл хотя бы 1 совпадение из категории `search_information`. Схема:
1. Keywords нашли `search_information` триггер → **сразу параллельно** запускаем web search + LLM-классификатор
2. LLM подтвердил intent → используем результат web search (он уже готов, 0ms дополнительной задержки)
3. LLM отклонил intent → отбрасываем результат web search, отправляем оригинальный запрос в D-ID
4. Keywords не нашли ничего → LLM-классификатор решает (web search не запускаем заранее)

Это сокращает стоимость на 80-90% при сохранении скорости для релевантных запросов.

### 4.2 Проблема: Размер `<ext_source>` блока и лимиты D-ID

**Текущее ТЗ:** Не указан лимит размера подсказки.

**Проблемы:**
- D-ID Chat API имеет лимит на размер сообщения (обычно 2000-4000 символов, зависит от настроек агента). Если web search вернул длинный ответ + оригинальный вопрос — может не влезть
- Текущий код отправляет **всю историю** чата в D-ID (`messagesPayload` в `chatAction`). Если каждое сообщение обогащено ext_source — история быстро раздувается

**Улучшения:**
- Ограничить `<ext_source>` блок до **500 символов** (уже есть в техплане, добавить в ТЗ)
- **Критично:** НЕ сохранять `<ext_source>` блоки в `ChatMessage`. Хранить только оригинальный текст пользователя. Обогащать **только текущее** отправляемое сообщение, не историю
- Добавить отдельное поле `enrichedContent` в ChatMessage (nullable) — для аналитики, но не включать в историю чата при формировании `messagesPayload`

### 4.3 Проблема: Системные инструкции D-ID агента

**Текущее ТЗ:** "В системных инструкциях агента D-ID нужно добавить правило про <ext_source>."

**Проблема:** Это изменение делается через D-ID API (`didService.updateAgent`), а не в нашем коде. Нужно:
- Кто и когда обновляет промпт? Вручную? Через админку? Автоматически при деплое?
- Что если промпт перезатрётся при обновлении других настроек агента?

**Улучшение:** Добавить в ТЗ:
- Текст правила добавить в поле `instructions` агента через админку (Settings или Roles editor)
- Текст правила: `"If the user message contains a block <ext_source>...</ext_source>, use the information inside it to form your answer. Never mention that you received a hint — answer naturally as if you know this information yourself. The ext_source block contains verified real-time data from external search systems."`
- Автоматически добавлять это правило при создании/обновлении агента, если включён Source Routing

### 4.4 Проблема: OpenAI web_search API — конкретный endpoint

**Текущее ТЗ:** "Chat GPT Search API" — неточное название.

**Уточнение:** Использовать **OpenAI Responses API** (`POST /v1/responses`) с инструментом `web_search_preview`. Это новый API (заменяет Completions для use-cases с tools). Пример:
```json
{
  "model": "gpt-4o-mini",
  "tools": [{ "type": "web_search_preview" }],
  "input": "What has Trump said in the last 3 days? Return concise summary, max 500 characters."
}
```
Ответ содержит как текст, так и ссылки на источники (citations). Ссылки можно игнорировать для MVP.

### 4.5 Дополнение: Что делать при ошибке web search

**Не описано в ТЗ.**

**Добавить:**
- Если web search вернул ошибку (таймаут, 429, 500) → отправлять запрос в D-ID **без обогащения**
- Логировать ошибку в `ExternalServiceLog` (таблица уже существует в схеме)
- Не показывать пользователю ошибку — аватар просто ответит на основе своих знаний
- Если ошибки происходят > 5 раз подряд → временно отключить web search на 5 минут (circuit breaker)

## 5. Фото из блога / из интернета

### 5.1 Проблема: Google Custom Search API — квоты и стоимость

**Текущее ТЗ:** "Используем Google Custom Search API (внешние фото)."

**Проблемы:**
- Бесплатный лимит: 100 запросов/день. После — $5 за 1000 запросов
- Нужно создать Custom Search Engine в Google Console и настроить его на поиск изображений
- API ключ, CX (Search Engine ID) — дополнительные секреты в `.env`

**Улучшение:** Добавить в ТЗ:
- ENV переменные: `GOOGLE_CSE_API_KEY`, `GOOGLE_CSE_CX`
- Дневной лимит запросов (настраиваемый, default 80 — оставить запас до 100)
- Счётчик запросов в Redis (`google_cse_daily_count` с TTL 24h)
- Если лимит исчерпан → возвращать пустой массив, не ошибку
- **Альтернатива для рассмотрения:** Bing Image Search API (Azure) — 1000 бесплатных запросов/месяц, и Azure SDK уже используется в проекте (для Speech)

### 5.2 Проблема: Безопасность прямых URL картинок

**Текущее ТЗ:** "Прямой URL, без загрузки на сервер."

**Проблемы:**
- Google CSE может вернуть картинку с произвольного домена. Браузер заблокирует загрузку если CSP (Content-Security-Policy) не позволяет
- Картинка может быть удалена/перемещена — пользователь увидит сломанное изображение
- Hotlinking может быть запрещён на стороне источника (403 Forbidden)

**Улучшения:**
- Добавить fallback `onError` для `<img>` — показывать placeholder
- Добавить домены картинок блога и Google proxy в `next.config.ts` → `images.remotePatterns` (для Next.js Image optimization). Или использовать обычный `<img>` без Next.js Image, если домены непредсказуемы
- Для Google CSE: использовать `"imgSize": "large"` и `"safe": "active"` в параметрах — чтобы не показать NSFW контент

### 5.3 Проблема: UX при показе фото — не описан переход между аватаром и медиа

**Текущее ТЗ:** "Фото отображаются в виде галереи в медиа-панели сетка 2x2."

**Не описано:**
- Когда показывается медиа-панель? Одновременно с ответом аватара? До? После?
- Как скрывается? По клику? По таймеру? При следующем вопросе?
- Что если пользователь задал новый вопрос — медиа закрывается или остаётся?

**Улучшение:** Добавить в ТЗ поведение:
1. Медиа-панель появляется **сразу** после получения результатов поиска (не ждём ответ D-ID)
2. D-ID одновременно говорит "Вот фото что ты просил..." — синхронизация не требуется
3. Медиа-панель **остаётся видимой** до следующего запроса пользователя (не на таймере)
4. При новом вопросе — если новый ответ тоже содержит медиа → заменить контент. Если нет → плавно скрыть (fade out)
5. На мобильных: медиа-панель **под** аватаром (не рядом). Scroll до панели автоматически (smooth scroll)

### 5.4 Проблема: Фото по 4 штуки — может быть много или мало

**Улучшение:** Добавить адаптивную логику:
- Если найдено 1-2 фото → показываем в ряд (grid 1x2 или 1x1)
- Если найдено 3-4 → grid 2x2
- Не заполнять пустыми ячейками — динамический grid

## 6. Видео из блога / из интернета

### 6.1 Проблема: YouTube Data API v3 — квоты

**Текущее ТЗ:** "Используем YouTube Data API v3."

**Проблема:** YouTube Data API имеет квоту **10,000 units/day**. Один search запрос = **100 units**. Это = 100 поисков/день. При активном использовании может не хватить.

**Улучшение:**
- Добавить в ТЗ мониторинг квоты
- Кэшировать результаты поиска в Redis (TTL 1 час) — повторный запрос "yoga video" за час не тратит квоту
- Рассмотреть альтернативу: **oEmbed** для YouTube (бесплатный, без API ключа, но без search — только embed по URL). Для внешнего поиска — это не подходит, но для блога (где URL уже есть) — идеально

### 6.2 Проблема: YouTube iframe и приватность (GDPR)

**Улучшение:**
- Использовать `youtube-nocookie.com` для embed (privacy-enhanced mode)
- Добавить `loading="lazy"` для iframe — не загружать пока не видно

### 6.3 Проблема: D-ID говорит заготовленную фразу — как?

**Текущее ТЗ:** D-ID: "Говорит: Вот фото что ты просил, надеюсь я правильно тебя понял."

**Проблема:** Как именно D-ID произнесёт эту фразу?
- Через `chat()` API — нельзя, там D-ID сам генерирует ответ
- Через `sendStreamScript()` — можно, но это обходит историю чата

**Улучшение:** Описать конкретную механику:
- Вариант A: Отправить через `chat()` с модифицированным сообщением: `"Пользователь попросил фото из Турции. <instruction>Скажи коротко что нашёл фото по его запросу и предложи посмотреть. Не описывай сами фото.</instruction>"`
- Вариант B: Отправить через `sendStreamScript()` заготовленную фразу на языке пользователя, а в `chatAction` сохранить как ASSISTANT message для истории
- **Рекомендация:** Вариант A — D-ID ответит в своём стиле + сообщение попадёт в историю чата естественным образом

## 7. Дополнения — общие пробелы ТЗ

### 7.1 Отсутствует: Content Security Policy

Показываем контент с внешних доменов (Google Images, YouTube, фото блога). Нужно:
- Обновить CSP в `next.config.ts` или middleware: разрешить `img-src` для доменов блога и Google proxy
- Разрешить `frame-src` для `youtube-nocookie.com`

### 7.2 Отсутствует: Модель `MediaAsset` — связь с Agent

**Текущее ТЗ описывает `agentId` в MediaAsset.**

**Проблема:** Медиа из блога — общее для всех агентов (все роли Нейла имеют одинаковые фото из одного блога). Привязка к конкретному агенту создаст дубликаты.

**Улучшение:**
- `agentId` сделать **nullable**. Если `agentId = null` — медиа доступно всем агентам
- При парсинге из блога не привязывать к агенту — это общий контент
- При поиске: искать WHERE `(agentId = $1 OR agentId IS NULL)`
- Привязка к агенту нужна только если в будущем добавится специфичный контент для роли

### 7.3 Отсутствует: Модель Prisma — правильные типы ID

**Текущее ТЗ (`02-technical-plan.md`):** В схеме `PrerenderedVideo` и `MediaAsset` используется `Int @id @default(autoincrement())`.

**Проблема:** Вся текущая схема Prisma использует `String @id @default(cuid())`. Смешение `Int` и `String` ID — плохая практика.

**Улучшение:** Использовать `String @id @default(cuid())` как в остальной схеме. Также `agentId` должен быть `String` (не `Int`), как в текущей модели `Agent`.

### 7.4 Отсутствует: CRON для медиа — отдельный worker или расширение текущего?

**Текущее ТЗ:** "Оба обработчика работают по CRON: 1 раз в сутки."

**Проблема:** Текущий worker (`knowledge-cron-worker.ts`) уже парсит блог. Если добавить парсинг медиа в тот же worker — он станет ещё длиннее (уже 1000+ строк). Если сделать отдельный — два worker'а будут параллельно обращаться к API блога с одними и теми же credentials.

**Улучшение:**
- Расширить **текущий** worker: при парсинге поста (цикл `for (const post of newPosts)`) уже есть доступ к HTML. Добавить извлечение медиа **в том же цикле**
- Вынести логику парсинга медиа в отдельный файл (`src/lib/media/blog-media-parser.ts`), но вызывать из текущего worker'а
- **Не создавать** отдельный CRON контейнер — это усложнит инфраструктуру

### 7.5 Отсутствует: Обработка ошибок сети при внешнем поиске

Добавить в ТЗ:
- Все внешние API запросы (Google CSE, YouTube, OpenAI web_search) должны иметь:
  - Таймаут: 5 секунд
  - Retry: 1 раз с backoff 1 секунда
  - Логирование в `ExternalServiceLog`
  - Graceful degradation: при ошибке — возвращаем пустой результат, не ломаем основной flow

### 7.6 Отсутствует: Аналитика и мониторинг

Добавить в ТЗ:
- Логировать каждый классифицированный intent (тип, время классификации, использовался ли LLM)
- Логировать каждый внешний поиск (тип, время, количество результатов)
- Логировать показ медиа (тип, источник — блог/внешний, кол-во)
- Использовать существующую таблицу `ExternalServiceLog` с `level: INFO`

### 7.7 Отсутствует: Поведение при "что делать если не найдено ни одно медиа"

**Текущее ТЗ:** "Аватар говорит: К сожалению, я не смог найти подходящие фото/видео."

**Проблема:** Эту фразу должен произнести D-ID. Как?

**Улучшение:** Аналогично п.6.3:
- Отправить в `chat()` сообщение типа: `"Пользователь попросил фото/видео, но ничего подходящего не найдено. <instruction>Скажи что не смог найти подходящие медиа по запросу, предложи уточнить запрос или спросить что-то другое.</instruction>"`
- D-ID сам сформулирует фразу в стиле Нейла

### 7.8 Отсутствует: Кэширование результатов поиска

Добавить в ТЗ:
- Кэш результатов web search в Redis: ключ = hash(query), TTL = 5 минут
- Кэш результатов медиа-поиска в Redis: ключ = hash(agentId + type + keywords), TTL = 10 минут
- Кэш результатов Google CSE: ключ = hash(query), TTL = 1 час
- Кэш YouTube search: ключ = hash(query), TTL = 1 час
